# 恢复与训练状态:算法笔记

> 本文是 body-watcher 全部确定性算法的学习笔记 + 实现说明:每个模型写清楚**出处、公式、直觉、我们的适配和局限**。
> 代码位置:`src/lib/recovery.ts`(恢复侧)、`src/lib/training-status.ts`(负荷侧)、`src/lib/readiness.ts`(今日建议合成)。
> 数据流:原始数据(手环/训记)→ 基线与特征 → 确定性算法(本文)→ 仪表盘展示 + LLM 引用解读。

---

## 0. 总览:三个数字各回答一个问题

| 数字 | 回答的问题 | 核心输入 |
|---|---|---|
| **恢复分 0-100** | "身体从昨天恢复得怎么样?" | HRV、静息心率、睡眠债 |
| **训练状态(ACWR + Form)** | "最近的训练量和身体能力比,处于什么位置?" | 训练负荷序列 |
| **今日建议(Readiness)** | "所以今天到底练不练、练多狠?" | 恢复分 × 训练状态合成 |
| **睡眠需求** | "今晚该睡多久?" | 睡眠均值 + 债务 + 昨日负荷 |

所有指标的共同前提:**和自己的基线比,不和别人比**。

## 1. z-score 基线(一切的地基)

**出处**:Whoop 公开方法论;Plews et al. 2013 证明 HRV 的个体内日间波动 远小于个体间差异,所以"自己 vs 自己的均值"才有意义。

**公式**(2026-09-24 起改为 30 天鲁棒基线,见下):

```
基线池 = 除今天外、最近 30 天的样本(缺数据的日期自然跳过)
中心 = 中位数;离散 = MAD × 1.4826(正态分布下与标准差同尺度)
z = (今天值 − 中心) / 离散
```

**实现细节**:
- HRV 优先用**深睡期 rMSSD**(`hrv_rmssd_deep_ms`),缺失退回全天均值——深睡期副交感神经主导,信号更干净,也是 Whoop 取数的时间窗；HRV 的 z-score 改在 **ln(ms) 空间**计算(右偏分布取对数更接近正态),`baselineMean` 仍回显原始 ms(`exp(ln 中位数)`),字段名保留不破坏消费方
- **样本 ≥ 5 天才出 z-score**(`ready` 标志),否则只展示原始值。太少样本的离散度不可信,z 会乱跳
- **离散下限**(2026-09-24 新增):样本少或设备给整数(RHR)时,MAD 可能被压到接近 0,放大无意义的 z 值——设下限 RHR ≥ 2.0 bpm、ln HRV ≥ 0.08、呼吸率 ≥ 0.5 次/分
- 静息心率方向相反:z 越高 = 越差(交感兴奋/未恢复)
- **为什么从均值/标准差改成中位数/MAD**(2026-09-24):病中几天的异常值混入基线池后,标准差会被明显拉宽("钝化"),之后哪怕恢复正常,z 也显得"没那么异常";中位数/MAD 对少数极端日更鲁棒,不会被两三个异常日显著带偏

**直觉**:z = -1.5 意思是"今天比你自己 95% 的日子都低"。绝对值(HRV 50ms)只说明体质,z 才说明**状态变化**。

## 2. 恢复分 0-100

**出处**:Whoop Recovery(HRV + 静息心率为主输入,SpO₂/呼吸率只做异常旗标)。加权与映射细节 Whoop 未完全公开,以下是我们按同一框架的落地。

**公式**:

```
z_hrv   = (今天lnHRV − 基线中心) / 基线离散        越高越好,ln 空间计算
z_rhr   = −(今天RHR − 基线中心) / 基线离散         取负:越高越差
z_sleep = −(睡眠债分钟数) / 45                    比近7天均值少睡45分钟记 -1

综合z = 0.4·z_hrv + 0.3·z_rhr + 0.3·z_sleep     各项与综合都夹在 ±3
恢复分 = Φ(综合z) × 100                          Φ = 标准正态累积函数
```

基线中心/离散见第 1 节(30 天鲁棒基线:中位数 ± MAD×1.4826,离散下限 RHR 2 bpm / ln HRV 0.08 / 呼吸率 0.5 次/分)。

**设计决策**(与 Whoop 的有意偏离):
- **睡眠债计入分数**(Whoop 不计):我们要的是"一眼看今天能不能练",昨晚只睡 6 小时却不影响分数不合理。睡眠正常时该项自然为 0,不日常压分
- **睡眠债口径**(2026-09-24 修正):`债务 = max(近7晚实际睡眠均值, 用户最低目标) − (⅔·昨晚 + ⅓·前晚)`。实际睡眠 = 在床 − 夜间清醒(躺 8 小时醒 1.5 小时不算睡满);缺一晚数据时用另一晚顶上。改为加权两晚而非只取较差一晚,是因为单纯"取两晚最差"在两晚都是正常睡眠时仍可能计出债务(两晚都略低于均值时,较差一晚被当成唯一依据,偏离参照线的幅度被放大);加权版在两晚都等于均值时债务为 0,同时连续差睡眠依然能被及时反映,不会像单晚口径一样被 7 日均值自己的下滑"稀释"掉。参照线"取较高者"是防"越缺越正常":连日缺觉时均值不能向下兼容,设了目标就以目标为底线;设备缺数据时(daily_health 的 sleep_hours/hrv/resting_hr 按日补缺,`src/lib/health-merge.ts`,设备优先)也能靠目标算债。三档目标(min/target/ideal)在 /settings 配置,存 `app_settings` 表,见第 7 节
- **Φ 映射的含义**:完全等于自己的正常水平 = **50 分**;+1σ ≈ 84;-1σ ≈ 16。所以分数天然是"你历史分布里的百分位"
- **权重 40/30/30**:HRV 是文献里最强的单一恢复信号;RHR 次之;睡眠债是修正项

**降级规则**(Whoop 不用操心,我们必须处理):
| 情况 | 行为 |
|---|---|
| HRV 基线 < 5 天 | 整体不出分(核心信号缺失,出分是编造) |
| 今晚某项缺失(未佩戴/未同步) | 权重归一化,剩余项分摊 |
| SpO₂ < 90% 或呼吸率 > 基线+1σ | 不参与计算,挂旗标,分数封顶 66(黄色档) |

**分档**:<34 红(只轻松恢复)/ 34-66 黄(正常练)/ ≥67 绿(可上强度)。

**主要拖累项**(2026-09-24 新增):取 `z × 权重` 最负且 z ≤ −0.5 的一项(HRV / 静息心率 / 睡眠),生成一句话说明,如"静息心率比基线高 3 bpm""HRV 低于基线 12%""睡眠比参照线少 40 分钟",在恢复分下方展示。没有任何一项满足条件时不显示(不是"总得挑一个最差的"）。

> **切换日 2026-09-24**:以上基线/睡眠债改动从这天起生效。此前 `recovery_snapshots` 落档的分数用的是旧口径(21 天 / 均值±标准差 / 睡眠债取两晚较差一晚),与新算法不可直接比较,月报跨越切换日会看到口径跳变。

## 3. 训练负荷 sRPE-TL(后面两个模型的原材料)

**出处**:Foster et al. 2001,session-RPE Training Load。力量训练没有分钟级心率(传统 TRIMP 需要),sRPE 是学界标准替代:**主观负荷 × 时长**,两者相乘正好抓住了"强度×剂量"。

**公式与量纲**:

```
负荷(AU)= RPE(0-10) × 时长(分钟) / 6
```

`/6` 是我们的量纲归一:RPE10 练 1 小时 = 100 AU。这样典型一次训练在 50-80 AU,对齐 TrainingPeaks TSS 的经验量纲,下面的 Form 分区阈值才能沿用。**直接用原始 sRPE 量纲(400+/次)会让 TSB 的 ±5/±10 阈值完全失效**——这是实现时最容易踩的坑。

**无 RPE 模式**(训记没有 RPE 录入入口时):

```
估计RPE = clamp(1 + 总组数×0.25 + 时长/30, 1, 10)
```

例:15 组/53 分钟 ≈ 6.5(中高强度);7 组/25 分钟 ≈ 3.5(轻)。组数/时长捕捉不了接近力竭的程度(sRPE 的本意)，所以这不是精确 RPE 的替代品。所有会话都缺 RPE 时，系统开启无 RPE 模式：估算负荷只用于观察长期趋势，`ACWR <0.8` 不会触发加量或冲强度建议；高负荷预警仍会保留。哪些天用了估计值,序列里带 `estimated` 标记,UI 和 LLM 都会声明；训练时开启手环运动模式后，可用心率负荷作并行对照。

**休息日负荷 = 0**:这点很重要——休息日的"0"参与了 EWMA 衰减,是 form 回升的来源。

## 3.5 心率负荷对照(Fitbit 四区 TRIMP,并行指标)

**出处**:Foster TRIMP 的区间加权思路。2026-09-10 实测确认 Google Health API 的
`exercise` 会话自带手环(Fitbit Air)算好的心率汇总:`averageHeartRateBeatsPerMinute`
与 `heartRateZoneDurations`(light/moderate/vigorous/peak 四区停留秒数),同步时落进
`google_daily_metrics`(列 `exercise_avg_hr` / `exercise_zone_*_s` / `exercise_calories`),
历史数据由 `scripts/backfill-exercise-hr.ts` 从 `google_raw_data` 回填。

**公式**:

```
心率负荷(AU) = (轻区秒 + 中区秒×2 + 剧烈秒×3 + 峰值秒×4) / 60
```

区间系数取 Foster 五区制前四档。量纲刻意与 sRPE 对齐:46 分钟轻区 ≈ 46 AU,
两条日负荷序列可直接对照(`trainingStatus.hr`,同窗口同 EWMA 核心的并行 ACWR)。

**怎么用(互查,不替代)**:力量训练里心率滞后于用力,sRPE 才是负荷主口径(第 3 节);
心率侧的价值在交叉验证——

- 两侧方向一致 → 结论更可信;
- RPE 侧"负荷偏低"而心率侧负荷不低 → 多半是 RPE 漏填(均值被 0 分/缺分拉低),先查心率侧再下结论;
- 心率侧 `daysWithHr` 少 → 用户训练时没开手环运动模式,此时心率侧缺数据≠没练,不要拿它否定 RPE 侧。

**已知限制**:`heart-rate` 原始序列(~2.4s 一个采样,全天 4 万点)不支持服务端时间过滤,
全量入库成本高,暂不落库;分区数据只覆盖"开了运动模式"的会话,被动识别的心率不进负荷。

## 3.6 手环会话(时长修正 + 额外活动)

**出处**:用户反馈训记计时不准(2026-09-23 实测:训记记 12 分钟,手环 WORKOUT 实测 52 分钟),且打球等非力量训练只在手环里有数据,训记完全不记录。代码:`src/lib/session-merge.ts`(纯函数),数据源 `google_exercise_sessions`(同步时 upsert;老备份无此表时由 `sessionsFromRawPayloads` 直接从 `google_raw_data` 解析)。

**时长修正** `correctDurations(logs, sessions)`:

- 取当日 `exercise_type = 'WORKOUT' AND recording_method = 'ACTIVELY_MEASURED'`(手动开启运动模式的力量训练)的会话,`active_minutes` 求和记为 W。
- 当日**恰好 1 条**训练记录时:`duration = max(原 duration, W)`,标记 `durationSource: "wearable"`。
- 当日**多条**训练记录时不修正——无法可靠配对到具体哪一条(历史上只有一次手动+训记重复的场景,当时没有手环数据)。

**额外活动** `extraActivities(sessions)`:识别"训记之外、手环记到的运动"(打球、游泳、徒步等),按心率负荷折算计入训练负荷。

1. 排除 `WORKOUT`(已在时长修正里处理)、`WALKING`、`BIKING`(走路/通勤,不算训练)。
2. 其余会话按开始时间排序,前一段结束到后一段开始间隔 **≤10 分钟**的合并为一组(如热身有氧接正式比赛)。
3. 组内 `中区 + 剧烈区 + 峰值区` 秒数合计 **≥30 分钟**才计为一次额外训练;负荷 = `心率负荷(第 3.5 节公式) × 0.5`。
   折半系数 `EXTRA_HR_LOAD_FACTOR = 0.5`:心率四区负荷对有氧/球类场景约为 sRPE/6 口径的 2 倍
   (实测:9/19 打球含轻度区的四区心率负荷 ≈182 AU,×0.5≈91 AU,对照 RPE7×80 分钟/6 ≈ 93 AU,比值约 2.0),
   折半后与力量训练的 sRPE 负荷同量纲。
4. 返回 `{ date, minutes, load, label }[]`(`label` 取组内时长最长会话的中文类型名,如"球类")。

**接入训练状态**:`computeTrainingStatus` 的 `opts.extraActivities` 在日负荷序列里按日累加,计入 `sessions` 但不计入 `estimatedSessions`(`allSessionsEstimated` 只看训记训练是否都缺 RPE)。`TrainingStatus` 新增 `durationCorrected`(时长被手环修正的训练次数)与 `extraActivities`(窗口内计入的额外活动列表),训练状态卡据此展示"N 次训练时长按手环修正"与"9/19 打球 81 分钟"之类的条目。

## 4. ACWR 急慢性负荷比(训练状态主指标)

**出处**:Williams et al. 2017(EWMA 版);Gabbett 2016 把 ACWR 带火(《The training—injury prevention paradox》)。

**公式**:

```
急性负荷 acute   = EWMA(近 7 天负荷),  λ = 2/(7+1)  = 0.25
慢性负荷 chronic = EWMA(近 28 天负荷), λ = 2/(28+1) ≈ 0.069
ACWR = acute / chronic
```

EWMA(指数加权移动平均):`today = λ·x + (1−λ)·yesterday`,越近的日子权重越大,且**永远不截断历史**(普通 7 日均值会突然遗忘 8 天前的大课)。λ=2/(τ+1) 是 EWMA 等效 τ 天窗口的标准换算。

**分区表**:

| ACWR | 状态 | 解读 |
|---|---|---|
| < 0.8 | 负荷偏低 | 慢性负荷高于近期;是否有"加量空间"还要看恢复分与是否处于回归期(第 4.5 节),不能只凭 ACWR 下结论 |
| **0.8 – 1.3** | **最优区间** | 急性和慢性匹配,甜蜜点 |
| 1.3 – 1.5 | 偏高 | 短期冲量,不再加量 |
| > 1.5 | 急性峰值 | 相对平时突变,Gabbett 统计的伤病风险区 |

**已知争议**(诚实记录):Impellizzeri et al. 2020 批评 ACWR 数学上就是把"近期负荷"和"远期负荷"相除,不比直接看负荷量更有预测力,且慢性负荷未必代表"适应"。我们仍采用它,因为:(a) 阈值直觉好用;(b)EWMA 版规避了原版滚动窗口的阶跃问题;(c) 和 Form 互相印证,不单独做决策。

**数据要求**:≥14 天才出值(chronic EWMA 半衰期约 10 天,太短是噪声);28 天几乎无训练则不出值。

## 4.5 回归期(停训/生病后的逐周负荷上限)

**出处**:用户反馈"训练状态总显示负荷偏低,判断只看训练量、不看身体情况"——停训或生病后 ACWR 走低是身体的合理表现,不该直接解读成"可以加量"。代码:`src/lib/load-context.ts`(纯函数),挂在 `DailyContext.loadContext`。2026-09-24 新增。

**进入条件**(满足任一):

- **停训**:近 28 天内结束(或仍在持续)的、连续 **≥7 天**日负荷为 0 的区间,且该区间之前 28 天内有训练负荷(28 天窗口是为了保证空窗结束后 21 天的回归期都能被识别到)。
- **生病**:近 **14 天**内"信号日"≥2 天。信号日 = 当日睡眠皮肤温度比设备基线高 ≥1.0°C,或呼吸率比前 30 天中位数高 ≥1.0 次/分(前序样本需 ≥5 天才判定,避免样本太少的误判)。单日异常不触发(可能是噪声)。

两者同时满足时按"生病"(`reason = "illness"`)展示文案。

仅生病、从未连续停训 ≥7 天时(训练节奏一直维持,只是信号日异常),中断起点取"近 14 天窗口内仍留存的最早信号日"——随着时间推移、较早的信号日滚出 14 天窗口,这个起点会跟着右移,`baseWeekly`/本周上限也会跟着重新计算;这种纯生病场景的回归期最晚在最后一个信号日之后 14 天结束(仍受下方"退出条件"约束,不会更晚)。

**基准周负荷** `baseWeekly` = 中断起点之前 28 天总负荷 ÷ 4(中断起点:有空窗时取空窗首日,否则取窗口内首个信号日)。为 0 时不给出上限数字,只提示处于回归期。

**恢复训练日** `resumeDate` = 空窗最后一天与最后一个信号日两者中较晚的一天**之后**的第一个训练日。尚未恢复训练时仍处于回归期,周序号记为 0("尚未恢复训练"),上限按第 1 周系数给出。

**回归周与上限**:`week = floor((今天 − resumeDate) / 7) + 1`;本回归周已练负荷 = `resumeDate + 7×(week−1)` 到今天的负荷之和;上限 = `baseWeekly × 系数`,系数按周递增:

| 回归第几周 | 上限系数 |
|---|---|
| 第 1 周 | 0.6 |
| 第 2 周 | 0.8 |
| 第 3 周 | 1.0 |

超过本周上限**只追加提示,不降档**(用户 2026-09-24 选定:回归期的核心风险是加量过猛,不是当天偏保守的 ACWR 读数;已经练到位了不该因为"算法读数高"反而建议休息)。
注意这只针对"本周回归额度用完"这一种信号——ACWR 急性峰值(risk)和 form 疲劳积累这两道护栏**不受回归期影响**,见下方"今日建议合成"的更正。

**退出条件**(满足任一):

- 距 `resumeDate` ≥ 21 天(给足 3 个回归周);
- **粘性退出**:`resumeDate` 到今天之间,**曾经存在**任意一天 `d`,其近 7 天负荷(以 `d` 为终点)≥ `baseWeekly`——一旦命中就此退出回归期,不会因为后续几天没练、那次达标的负荷滚出 7 天窗口又"弹回"回归期(真实场景:9/19 打球后负荷达标、9/23 仍在窗口内,但到 9/26 窗口已滚动,若只看"今天"的近 7 天会错误地判回回归期)。

**与今日建议合成**:回归期内的负荷判定护栏**不关闭**——

- ACWR 处于 `risk`(急性峰值)区 → 仍走 `deload`(主动降档),理由文案与非回归期一致;
- 否则 form 处于"疲劳积累" → 仍走 `hold`(不再加量);
- 否则才是新增的 `LoadBand = ramp`:查表后的结论永不输出"可以冲"(`go_hard`);本周额度用完时结论不变(仍是回归期该有的练法),只在说明文案里追加"本周回归额度已用完,今天维持量,别再加",`ramp` 的说明文案始终带上 ACWR 读数(如"……；ACWR 1.40 偏高"),不会因为处于回归期就把高位 ACWR 读数藏起来。

**已知局限**:

- 空窗(停训)长于训练/会话取数的 63 天历史窗口时识别不到回归期——判定停训需要"空窗之前 28 天内有训练负荷",如果空窗本身就超出了 63 天历史窗口,窗口里压根看不到空窗前的训练记录,自然判不出"之前有练"。
- 平时训练节奏本来就≥8 天一次的人,只要出现一次正常的训练间隔就会被当成"停训"触发回归期——`findRecentGap` 单纯按"连续 ≥7 天零负荷"识别,不区分这是真的停训还是用户一贯的低频节奏。

## 5. Form 体力-疲劳(Banister 冲击-响应模型)

**出处**:Banister 1975 的 fitness-fatigue 模型;实践化的是 TrainingPeaks 的 CTL/ATL/TSB 体系(自行车圈标准)。

**公式**:

```
fitness (CTL,慢性适应) = EWMA(负荷, λ = 2/43)   τ≈42天,长得慢
fatigue (ATL,急性疲劳) = EWMA(负荷, λ = 2/8)    τ≈7天,掉得快
form (TSB) = fitness − fatigue
```

**直觉**:体力和疲劳都是负荷的影子,但**时间常数不同**——练完当天疲劳(+ATL)比体能积累(+CTL)涨得快,所以连续大练 form 变负;停练几天疲劳快速衰减、体能还在,form 转正 = "新鲜"。

**分区表**(TrainingPeaks 经验值,量纲依赖第 3 节的 AU 归一):

| form | 状态 | 解读 |
|---|---|---|
| > +5 | 新鲜 | 疲劳已散,适合测试/冲 PR/比赛 |
| −10 ~ +5 | 平衡 | 正常训练带 |
| < −10 | 疲劳积累 | 减量或安排恢复日 |

**手算对照**(实现时验证过):21 天每天 100 AU 后停练 7 天 → CTL≈72、ATL≈13、form≈**+58(很新鲜)**;恒定负荷 → form=0。

## 6. 单调性与 Strain(Foster 的过度训练雷达)

**出处**:Foster 1998。回答 ACWR/form 都不回答的问题:**负荷内容是否太单一**。

```
单调性 monotony = 近 7 天日均负荷 / 日负荷标准差
strain         = 周总负荷 × 单调性
```

- 单调性 > 2 预警:每天练得差不多(比如天天同量)意味着没有高低起伏,恢复节奏被抹平——Foster 观察到的过度训练案例多发生在此
- 标准差→0 的极端(全周完全一样)在数学上趋于无穷,实现里封顶 10(表达"极高"足够)
- strain 把"量"和"单一性"乘在一起:周负荷 2000 且单调性 2.5 = strain 5000,比同量但高低起伏(strain≈2000×1)危险得多

## 7. 睡眠需求推荐

**公式**(Whoop Sleep Coach 的简化落地 + 用户三档目标):

```
地板 base = max(近7晚在床均值, target目标)     设了目标就不被低均值带塌
债务补偿   = clamp(睡眠债, −90, +180) / 3      只还 1/3,不鼓励一次补爆
负荷补偿   = 昨日负荷 >250 AU ? +20min : >100 AU ? +10min : 0
需求 = clamp(base + 债务补偿 + 负荷补偿, 5h, min(ideal理想 ?? 12h))
结果取整到 10 分钟
```

**三档目标**(在 `/settings` 设置,存 `app_settings` 表,分钟数,任一档可留空):

| 档 | 作用 | 生效处 |
|---|---|---|
| **最低 min** | 睡眠债参照线 `max(7晚均值, min)`——跌破即欠觉,拖累恢复分 | 第 2 节睡眠债 |
| **目标 target** | 今晚建议的地板 `max(均值, target)`——建议不会低于它 | 本节 |
| **理想 ideal** | 今晚建议的封顶——设了就不过度补觉 | 本节 |

三档全空 = 完全回到"纯历史均值"口径(原行为)。设 min ≤ target ≤ ideal 的顺序由 API 校验。

例(无目标):均值 7h54m + 债 90 分钟(+30) + 昨日大课(+20) → 建议 8h40m。
例(target=7h30m、近 7 晚均值只有 7h):地板抬到 7h30m 起算,而不是从 7h 起——这就是"越缺越正常"陷阱的堵点。

## 8. 今日建议 Readiness(恢复 × 负荷合成)

**出处**:Akiyama et al. 2016(ML 分析 14063 条跑者主客观状态记录:"是否运动"由主观状态/肌肉痛/计划驱动,而"练多狠"主要由睡眠与疲劳驱动)——我们的两层规则是其手工落地。产品动因:训练状态卡对睡眠完全无感,"ACWR 最优"会被读成"今天状态好";恢复与负荷必须合成一条明确的行动结论。

**输入分两路,职责严格分开**:

```
恢复侧(决定练多重):恢复分 ≥67 good / 34-66 且无异常旗标 ok / 34-66 且有异常旗标 low / <34 bad
负荷侧(决定练不练):ACWR risk→deload / high→hold / under→build(仅恢复 good 时)/ 其余 maintain;
                   form 疲劳积累时封顶 hold;单调性>2 取消 build;
                   回归期(第 4.5 节):risk 仍→deload、疲劳积累仍→hold(护栏不关),
                   否则→ramp,永不输出"可以冲",说明文案带上 ACWR 读数
```

**门槛改动**(2026-09-24):原先 ok/low 以恢复分 50 分为界,等于把"个人常态"(Φ 映射下 50 分)自己劈成两半,一半正常日落进 low 被判"主动降档"。改为以**异常旗标**(血氧低/呼吸率高/体温高)区分 34-66 区间内的 ok/low——旗标才是"有没有需要留意的异常信号"的真实判断依据,分数本身在这个区间内的小幅波动(如 38 分 vs 45 分)只是日常波动,不该单独触发降档:

| band | 现在 |
|---|---|
| good | ≥67 |
| ok | 34–66 且无异常旗标 |
| low | 34–66 且有异常旗标 |
| bad | <34 |

**恢复分未就绪时(冷启动)降级但不弃权**:用分项 z-score(睡眠债/HRV/RHR 任一 ≤−1σ)+ 近两晚内的手动睡眠自评(≤3/10)+ 旗标判断;只认负向证据,无线索默认 ok——宁可不提醒,不能乱喊停。恢复信号陈旧(未同步)同样按"未知→不拦"处理。

**查表合成**(恢复 × 负荷 → 可以冲 / 正常练 / 主动降档 / 今天休息):

| 恢复\负荷 | 有余量(build) | 健康(maintain) | 高位(hold) | 突变(deload) | 回归期(ramp) |
|---|---|---|---|---|---|
| good ≥67 | 可以冲 | 正常练 | 正常练(不加量) | 主动降档 | 正常练(回归期第 N 周,按上限循序加量) |
| ok 34-66 无旗标 | 正常练 | 正常练 | 主动降档 | 今天休息 | 正常练(同上) |
| low 34-66 有旗标 | 主动降档 | 主动降档 | 主动降档 | 今天休息 | 主动降档(回归期叠加恢复偏低,轻量为主) |
| bad <34 | 主动降档 | 主动降档 | 今天休息 | 今天休息 | 今天休息(回归期恢复差,先休息观察) |

`回归期(ramp)`这一列只适用于回归期内**既无 ACWR 急性峰值、也无 form 疲劳积累**的情形;回归期内一旦出现 ACWR risk 或 form 疲劳积累,就按`突变(deload)`/`高位(hold)`列的结论走,不查`ramp`列——护栏优先于"回归期从宽"。

回归期内本周额度用完(`remaining ≤ 0`)**只在说明文案追加提示,不改变上表结论**("本周回归额度已用完,今天维持量,别再加")——已经练到位不该被读数倒扣成"休息"。

**负荷偏低(ACWR < 0.8)的解读按恢复分门控**(2026-09-24 新增,替代"负荷偏低就能加量"的旧逻辑):仅 `recoveryBand === "good"` 时才是"有加量空间"(`build`);`ok` 为 `maintain`,文案"负荷偏少,按计划练";`low`/`bad` 同为 `maintain`,文案"低负荷合理,先恢复"——负荷低不等于"该加量",还要看身体当下能不能接得住。

要点:负荷侧坏(受伤风险)永远能拦住恢复侧好;恢复侧坏时,加量空间(build)也**不许冲**——恢复偏低还想补量只会把问题滚大。
训练完全没数据且恢复侧也没信号时返回 `unknown`(数据积累中),不给假结论。
同一函数喂 dashboard 与教练工具(`query_recovery_status.readiness`),卡片和教练对话不会互相矛盾。
代码:`src/lib/readiness.ts`,展示元数据 `READY_ZONE_META`。

## 9. 全局局限(读数时记住这些)

1. **没有分钟级心率** → 做不了 Whoop 式心血管 Strain(0-21)和真 TRIMP,负荷全靠 sRPE 代理。若日后 Google Health 能拉到心率序列,可以升级
2. **RPE 全空** → 前期负荷是估计值,ACWR/form 只能看趋势不能抠数值。填 RPE 是当前精度上限的关键
3. **基线在成熟期**(2026-09 起):恢复分和基线偏离陆续在 9/8-9/9 后生效,前期"基线累计中"是诚实降级,不是故障
4. **静息心率 70bpm 偏高**:手环的"静息心率"多半是全天最低值而非睡眠静息,与基线法兼容(一致来源即可),但绝对值别套用公开常模
5. 所有模型都是**群体统计的个体化应用**,不是生理测量——分区阈值是经验先验,以自己的体感校准为准
